# PetCare Manager launch readiness

Updated: 2026-10-19

## Current product boundary

The application has a shared-database, multi-tenant foundation for multiple stores: tenant memberships/roles, server-verified store selection, scoped business repositories, composite tenant foreign keys and tenant-owned photo checks. Legacy data migrates into `main`; operators can provision stores and owners, send membership invitations through the encrypted outbox, and create encrypted tenant exports. A self-service signup route is implemented behind `PUBLIC_SIGNUP_ENABLED=0`; owner access remains inactive until email verification and untouched signups are purged after seven days by the email worker. Local development keeps a no-email manual verification link. Store admins can request a background encrypted export for the selected tenant after password reauthentication; the separate worker audits completed jobs, encrypts the passphrase at rest while a job is pending, and retains the private artifact for a configurable 1–168 hours. Global user accounts support verified email and one-time password recovery links. Tenant IANA time zones, UTC `DATETIME` storage, DST-aware report ranges, local timestamp rendering and a one-time legacy +07 migration are implemented. Vietnamese and partial English are available across sales, account/store administration, onboarding, team access, exports, ownership transfer, audit views and error pages; system emails, some server messages, historical audit text and locale formatting are not fully localized. This remains short of a global SaaS launch: billing/plan limits, deletion lifecycle, full localization, tax/FX/currency-change policy, managed infrastructure and independent security review remain open. SMTP credentials and live delivery/abuse behavior still need provider-specific validation.

## Baseline implemented in this pass

- Production mode rejects example secrets, insecure session cookies, debug mode, blank/default database passwords, and `_dev`/`_test` databases. `TRUST_PROXY=1` enables Werkzeug `ProxyFix` for exactly one trusted proxy's client IP and HTTPS scheme; forwarded host and port remain untrusted.
- Response security headers include a restrictive same-origin Content Security Policy, clickjacking protection, MIME sniffing protection, referrer policy, and a camera-only Permissions Policy.
- Every response generated for an authenticated session carries `Cache-Control: private, no-store, max-age=0` and `Pragma: no-cache`, including HTML and JSON containing tenant data.
- Optional phone QR access validates its configured origin; production refuses LAN QR links over plaintext HTTP. Direct mobile-browser camera streaming still needs HTTPS; on a trusted local HTTP network the file input can open the native camera without enabling `getUserMedia`.
- Destructive confirmations use external JavaScript so the Content Security Policy can block inline scripts.
- Login failures are throttled across app workers in MySQL. Account keys are HMAC hashes rather than stored usernames or IP addresses; thresholds are 10 failures per account or 40 per address per 15-minute window.
- Password verification bounds both password length and encoded PBKDF2 rounds. Unknown usernames still perform a dummy hash check.
- A MySQL-backed `session_version` is signed into each session and checked on every request. Password changes and membership deactivation/reactivation revoke previously issued cookies; the additive initializer migration adds the column to existing installations. The first rollout invalidates older cookies once, so users must sign in again.
- Accounts can set/change a global email after current-password reauthentication. Email verification tokens and password-reset tokens are random, stored as SHA-256 hashes, single-use, expire after 24 hours and 30 minutes respectively, and are throttled in MySQL. Password reset is available only for verified addresses and increments `session_version`; the forgot-password response does not reveal whether an account exists. Email requests persist in an encrypted MySQL outbox and a separate worker sends SMTP with bounded retries. Production requires SMTP STARTTLS and a stable, separately managed `MAIL_OUTBOX_KEY`. Provider delivery, bounce/complaint handling, queue alerts and worker deployment still need live validation.
- Login redirects reject external hosts, scheme-relative paths, backslashes, and control characters.
- `/healthz` checks process liveness; `/readyz` checks web/MySQL/schema readiness. Email and tenant-export workers write privacy-minimal MySQL heartbeats; `/workersz` returns ready only when both worker types have a recent successful heartbeat (90-second freshness window). Email-worker maintenance prunes old instance rows after 30 days. Monitor `/workersz` separately so a queue outage is visible without taking otherwise healthy web processes out of service. This endpoint is a health signal, not alert delivery.
- Optional `/metrics` endpoint is disabled unless `OPS_METRICS_TOKEN` is configured with at least 32 characters. A bearer token protects aggregate queue depth/age and worker-up metrics; output excludes tenant IDs and job/account data. Scrapes are no-store and database errors return 503. This enables Prometheus-style monitoring but does not send alerts; the token must be held by a private monitoring system and redacted from proxy/access logs. See [operations guide](operations.md).
- Runtime MySQL traffic uses a bounded thread-safe pool per process; each checkout resets timezone/tenant session state. The Compose defaults can open up to 20 DB connections across two web workers plus the email and export workers; this is capacity planning, not production load-test evidence.
- A Gunicorn WSGI entry point and non-root Docker image are available. Media defaults to a persistent local volume in Compose; an S3-compatible adapter is available for shared durable storage, with private application-served reads.
- Image decoding/normalization has per-process backpressure via `IMAGE_PROCESSING_CONCURRENCY` (default 1, valid 1–4); with Compose's two Gunicorn workers that permits up to two simultaneous image operations per web container. Saturated uploads receive a retry response; multi-container capacity is process-local and still needs realistic memory/latency load testing before tuning upward. See [operations guide](operations.md).
- A local/Compose backup command packages one InnoDB database with pet/product photos, encrypts the bundle with AES-256-GCM, sets restrictive file permissions, records SHA-256 checksums, and verifies integrity without leaving plaintext in the output directory. A separately invoked decrypt command writes a private tar.gz only after authentication and checksum validation. This does not replace managed off-site backups, retention, point-in-time recovery, key management or restore rehearsals.
- New local photo uploads use POSIX directory/file modes 0700/0600. Before upgrading a POSIX host that already has local photos, run `python -m petcare.vision.secure_photo_permissions`; this tightens only UUID-named application photos (including new tenant-prefixed names) and leaves unrelated files alone. `MEDIA_STORAGE_BACKEND=s3` supports private S3-compatible storage for multi-instance deployments; use workload IAM where possible, block public access, enable provider-side encryption/versioning and keep access behind the app's tenant authorization.
- Stored pet/product image uploads use per-admin and per-network quotas persisted in MySQL (defaults 12 and 60 requests/minute), so limits carry across app instances; a per-process semaphore also caps simultaneous image decode/normalization. This check happens after the bounded request body is received, so deployment edge/WAF controls must still limit upload bandwidth and request frequency.
- Access logs omit query strings, since customer searches can contain personal information.
- Customer, product, pet and invoice index pages fetch 25 rows at a time from MySQL and preserve active filters when paging.
- Empty catalog searches no longer add ineffective `LIKE '%%'` predicates. The repeatable local baseline in `scripts/benchmark_catalog_search.py` uses temporary tables cloned from the MySQL schema with 20,000 synthetic rows per tenant and 35 warm runs per query; it rejects non-`_test` database names and writes no persistent data. Reproduction: `python scripts/benchmark_catalog_search.py --database petcare_shop_test --rows 20000 --runs 35`. On this local MySQL instance, rare-match paginated substring-search medians were 20.05 ms for products, 15.44 ms for customers and 17.34 ms for pets; count-query medians were 17.23 ms, 13.89 ms and 14.27 ms respectively. P95 page latency was 24.78 ms, 16.78 ms and 25.03 ms. `EXPLAIN` used the tenant-scoped B-tree indexes and estimated scanning about 10,000 tenant rows; the leading-wildcard predicate still checks rows within that tenant, and pet ordering uses filesort. This is a single-process, local, warm-cache synthetic baseline, not a production SLA or concurrency/load test. It does not justify changing substring semantics or adding speculative indexes at this scale; repeat against the selected managed MySQL instance, with concurrency and larger tenants, before setting launch capacity or switching to n-gram/full-text search.
- Invoice creation loads bounded first pages and provides authenticated, debounced server-side search plus independent pagination for customers, products and available pets; large catalogs no longer render into one HTML form.
- Admin activity history records successful login, logout, store switching, invoice creation/payment/cancellation, stock adjustments, customer/product/pet profile and status changes, and account creation/updates. Business changes are audited inside their MySQL transaction; session events use a tenant-validated transaction. Authentication audit data contains no IP address or password/token values. Failed-login protection retains only HMAC-keyed throttle counters for a short window; persistent security-event retention and access policy still need a production decision. The read-only `/activity/` page is admin-only and paginated.
- Product and pet photo replacement takes a locking read of the owning row before updating its media reference. This serializes concurrent replacements so cleanup observes the actual prior image; MySQL integration verifies the final referenced object is the only object left after two overlapping replacements.
- AI chat is limited to 20 requests per account and 120 per network address per minute, and image scans to 8 per account and 40 per network address per minute; these atomic limits are shared through MySQL across workers. Network identifiers are HMAC-keyed and not stored as raw IPs; the email worker prunes throttle rows older than one day during hourly maintenance. Configure `TRUST_PROXY=1` only behind the single trusted proxy described above so network quotas use the real client address safely.
- AI requests reject redirects and endpoint query credentials, cap response size, require HTTPS in production by default, and explicitly label provider configuration instead of claiming a live connection. Chat instructions are separated from user-editable shop data so catalog text is not granted system-prompt authority.
- Multi-store isolation is implemented in the shared MySQL schema. Every business row carries `tenant_id`; actor membership is revalidated on each request; repositories bind a verified tenant context; composite foreign keys prevent cross-tenant invoice/customer/product/pet/actor references. Store memberships own role and active state, while display name/password are global identity fields. Store admins cannot change global name/password for identities with multiple memberships (including inactive ones); users update their shared display name in account settings after password reauthentication. Store owners/admins can edit the selected tenant's display name and IANA timezone from **Cài đặt cửa hàng**; slug remains stable and currency stays fixed because FX/ledger conversion is not implemented. Profile changes are audited in the same MySQL transaction. New media identifiers include the tenant namespace and S3 keys live under `tenants/<id>/<category>/`; photo reads and exports reject mismatched namespaces. Legacy UUID-only photos remain readable, and replacement cleanup counts references across stores before deleting a legacy object. MySQL integration tests exercise two stores, duplicate catalog codes, cross-store lookups/invoice attempts, photo access, account identity changes, membership roles and store switching.
- Existing single-store rows are assigned to the `main` tenant by the idempotent migration. A schema migration marker tracks the one-time conversion of legacy +07 `DATETIME` values to UTC. The migration uses MySQL DDL, which auto-commits; take and validate a backup first, use the schema-migration account, and inspect the migration result before allowing production traffic.
- Tenants and owners can be provisioned with an operator-run interactive command or feature-flagged self-service onboarding. Store admins create single-use, seven-day membership invitations bound to a normalized recipient email; with SMTP configured the link is encrypted in the transactional outbox and sent asynchronously, and acceptance is restricted to the invited verified account or creates an account for that email. The manual development fallback retains the email binding but does not claim the address is verified. Admins can revoke unused invitations and cancel queued mail. Subscription billing and plan limits remain absent.
- Ownership handoff is available at **Tài khoản → Bàn giao chủ cửa hàng**: the current owner reauthenticates, chooses an active admin, and the target account must sign in and reauthenticate within 72 hours. The membership role change is atomic; the requester can cancel; each transition is audited and throttled. A current locking read plus tenant-row serialization prevents concurrent requests from creating multiple open handoffs under MySQL `REPEATABLE READ`. Email is an optional notice to a verified target address, not an authorization link. The former owner retains admin access; legal/business decisions about exclusive ownership and support recovery still need product policy.
- Public store signup is available behind the default-off `PUBLIC_SIGNUP_ENABLED` flag. Email and IP quotas are stored as HMAC-keyed throttle records. Signup creates the tenant, owner identity, inactive pending membership and verification token atomically; configured email is queued encrypted in that same transaction. Only verifying email activates memberships marked for onboarding. Local mode without SMTP displays a no-store one-time verification page; the email worker removes untouched signup reservations after seven days. Keep signup disabled until billing/plan limits, terms/privacy, edge abuse controls and live delivery are ready.
- `python -m petcare.database.export_tenant export <slug> <bundle.pcarexport>` and the admin **Tài khoản → Xuất dữ liệu cửa hàng** flow snapshot one tenant's records and referenced photos with a SHA-256 manifest, then encrypt them with AES-256-GCM using a passphrase-derived key. UI export requires the admin's current password, enters a durable MySQL queue, and is processed by `python -m petcare.services.tenant_export_worker_cli`; the worker rechecks active tenant-admin membership, renews a lease, retries transient failures, encrypts the queued passphrase under `TENANT_EXPORT_JOB_KEY`, then clears it at completion. Completed exports are audited, served only to the requesting admin, and deleted with their job record after `TENANT_EXPORT_RETENTION_HOURS` (1–168, default 24). Configure the same stable Fernet key for web and worker; during rotation, keep retired keys in `TENANT_EXPORT_JOB_FALLBACK_KEYS` until jobs encrypted with them have finished. Production multi-instance deployments must use `TENANT_EXPORT_STORAGE_BACKEND=s3` or a shared durable filesystem; local Compose shares a private volume across the two services. `verify` authenticates without extracting; `decrypt` creates a new 0600 ZIP only after authentication and checksum verification. The encrypted output excludes password/token hashes and never overwrites an existing object key. Keep the user passphrase separately; forgetting it makes the export unrecoverable. Tenant deletion/retention remains unimplemented.

The current `.env` has no external AI model configured and image AI is off. The assistant does not call an AI provider in local mode; in SaaS, browser requests still reach the application server. Image queries are processed by the application server and are not saved as pet records; when AI Vision is enabled, the query is sent to the configured endpoint. Local image ranking is a visual hint, not an animal detector, identity match, or calibrated probability. It now weights a center crop for color, but full-frame structure and framing still affect results. Common English species/color/pattern/shape terms from a vision model are normalized against Vietnamese store metadata; this glossary is not full UI localization or a validated zoological taxonomy. Existing descriptors remain compatible and can be rebuilt with the dry-run-first batch command `python -m petcare.vision.reindex_pet_descriptors`. Live model quality, latency, cost and provider privacy have not been verified in this environment.

## Must complete before a public production deployment

1. Create a dedicated production database, a DML-only runtime user, and a separate schema-migration user. The app uses `DB_USER`/`DB_PASSWORD`; `python -m petcare.database.initialize` requires `MIGRATION_DB_USER`/`MIGRATION_DB_PASSWORD` in a one-off migration process in production and rejects a shared account or mismatched database. Set `DB_SSL_CA` to a read-only mounted provider CA bundle; production verifies the MySQL certificate and hostname. Test the TLS handshake against the provider endpoint and confirm the negotiated encrypted connection before release. Follow [database privilege setup](database_privileges.md). Back up first, migrate, verify every legacy row belongs to `main`, then start the release. Never run demo seed on it.
2. Set a unique random `SECRET_KEY`, strong DB credentials, `APP_ENV=production`, `COOKIE_SECURE=1`, `PUBLIC_BASE_URL=https://<trusted-domain>`, and TLS termination. `PUBLIC_BASE_URL` supplies absolute membership invite links and production rejects non-HTTPS or userinfo/query/fragment values. Set `TRUST_PROXY=1` only when exactly one trusted reverse proxy sits in front of the app and it overwrites forwarded IP/protocol headers.
3. Deploy behind HTTPS with edge rate limits/WAF, request-size limits, and a managed secret store. The app itself has login throttling; other expensive endpoints still need edge limits.
4. Configure managed MySQL backups, retention, point-in-time recovery, alerting, and rehearse a restore from the managed production backup. A local Compose rehearsal using the isolated test database passed on 2026-10-18; the repository utility does not provide off-site retention, scheduling, centralized key management or point-in-time recovery. Back up photos as well as SQL data.
5. Provision a private S3-compatible bucket, least-privilege workload identity and retention/versioning policy; test upload/read/delete for pet/product photos and encrypted export artifacts against the chosen provider before running more than one app instance. Configure `MEDIA_STORAGE_BACKEND=s3`, `TENANT_EXPORT_STORAGE_BACKEND=s3`, `MEDIA_S3_BUCKET` and `MEDIA_S3_REGION`; a custom endpoint must use HTTPS in production. Set one shared stable `TENANT_EXPORT_JOB_KEY` in web and worker. The local backup utility refuses S3 mode rather than silently omitting remote photos. Provider-managed bucket protection and a restore rehearsal are still required.
6. GitHub Actions now defines a Python 3.10–3.13 test matrix against disposable MySQL 8.4, dependency auditing with `pip-audit`, a Bandit source scan against a reviewed 38-finding baseline, a Trivy secret scan over the full source tree, and a Trivy production-image scan for HIGH/CRITICAL vulnerabilities and secrets. Local source-tree and image scans passed on 2026-10-18; the source scan reported zero findings, while the image had no fixable vulnerability findings at those severities and no secrets. A derived image containing a public synthetic GitHub token was correctly blocked by Trivy with a CRITICAL finding, confirming the secret scanner is active. `.trivyignore.yaml` contains four narrowly scoped, expiring exceptions for inaccurate third-party SBOM package versions, documented in the file. The hosted workflow has not yet run; require a green hosted run for each release and have an independent reviewer assess the baseline exceptions and security-sensitive changes.
7. Define an audit retention/access policy, including how long successful session events and failed-login throttle counters are retained and which support roles may inspect security data. Business record/profile changes are audited without copying personal field values or photo content into the log.
8. Before enabling public signup, add subscription/billing and plan limits, reviewed terms/privacy and data-retention policies, edge abuse controls and live SMTP validation. Independently review tenant isolation, tenant deletion/retention and per-tenant backup/restore boundaries beyond the current integration tests. Email verification/recovery, invitations and feature-flagged onboarding are implemented; bounces/complaints and queue alerts remain open. An admin can download an encrypted export for their selected store; the data-rights workflow still needs policy and independent review. The local manual-link fallback is for development only and does not prove mailbox control.
9. Complete localization for every route, form, validation/flash message, status, email and generated document, then verify date/number/currency formatting per locale. The selected UI language now persists on the global account identity across browser sessions and stores. Then define supported currencies, tax and FX/currency-change flows, customer data rights, support, incident response, and AI-provider data retention/region. Money uses `DECIMAL`/`Decimal`, current tender currency precision, tenant onboarding currency and invoice currency snapshots. Each tenant can choose a validated IANA timezone; database timestamps are canonical UTC and reports use DST-aware store-local date boundaries. Tax/FX/change-currency workflows are absent; global launch remains gated on those choices and legal operations.
10. Catalog substring search now has a preliminary synthetic baseline at 20,000 rows per tenant (see above). Still benchmark the selected managed MySQL instance under concurrency and larger tenant sizes, and set an explicit latency/capacity threshold before deciding whether to add n-gram/full-text search. Image search now uses tenant-scoped SimHash LSH buckets; the full photo descriptor still decides final ranking. A disposable MySQL 8.4 benchmark with 20,000 synthetic pets and 1% candidate selectivity (200 candidates) measured 114.87 ms median / 149.60 ms max across three warm full-service runs. When all 20,000 profiles shared the query hash, the candidate cap correctly selected full-scan fallback: 1,149.27 ms median / 1,276.62 ms max. The benchmark uses temporary tables and leaves persistent tables untouched. These generated hashes are controlled performance fixtures, not a representative recall set; production-size latency, concurrency, and recall against labeled photos still need measurement. The LSH result is approximate and may omit some visually similar profiles; the UI says so. Reindex existing photos with dry-run first, then `python -m petcare.vision.reindex_pet_descriptors --apply` to update descriptors and tenant-scoped buckets.
11. Configure the protected metrics endpoint in the private monitoring system; add alert delivery and edge rate limits/WAF. Queue depth/age, retained failed jobs and worker liveness are exposed, but the app does not page operators. Application quotas reduce AI and image abuse per account and shared network address but do not replace edge-level denial-of-service protection.

## Production container notes

For local Compose development, initialize before starting the web container: `docker compose run --rm web python -m petcare.database.initialize`, then `docker compose up -d --build web`. The production migration must run as a separate one-off job with migration credentials injected from the deployment secret store; do not place them in the long-running web service. The application refuses production mode unless `SECRET_KEY` is explicitly configured; a random per-process fallback is only for local development.

`docker compose up -d --build web email-worker export-worker` runs Gunicorn, the mail and export workers, and MySQL locally, with the web port bound to loopback. The production environment must deploy both workers with their matching secrets and shared database/object storage, use a database name that does not end in `_dev` or `_test`, set secure cookies, and put a trusted HTTPS reverse proxy in front. Do not expose the development Flask server or MySQL port to the public Internet.

The Compose stack is a single-host deployment aid, not a globally redundant architecture. Use managed database/object storage, TLS, monitoring, and a deployment platform with health checks for a public pilot. Multi-region availability, signup billing/plan controls, SaaS operations and localized commerce still require additional architecture/work.
